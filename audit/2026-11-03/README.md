## Already confirmed by hand (before the auditors reported)

- `v6y dev` claims to reload `v6y.config.ts` on every report, but Node caches ESM imports, so edits are ignored until restart (probe: re-importing an edited `.mjs` returned the old value). Fix: cache-bust the import URL with the file's mtime.
- A snapshot for a screen whose source file was deleted keeps reporting its issues (and failing `check`) forever. Fix: skip issues whose file no longer exists, with a count in the output.
- `v6y fix` resolves `issue.source.file` with `path.join(cwd, file)`, so a crafted snapshot with `../` could make it edit a file outside the project. Fix: resolve and require the path to stay under `cwd`.

## Findings by severity


### Critical

- **fix writes syntactically broken source when an insertion and a removal land at the same offset** (`packages/cli/src/fix.ts:185`; bug; from cli-mcp-fix; confidence 1)  
  Claim: When one element gets an add-attr (inserted at opening.name.end) and a remove-attr whose attribute is the first one (its removal range also starts at opening.name.end), the splices are applied in the wrong order with offsets from the original text, so the removal slices through the just-inserted text and corrupts the file.  
  Evidence: Ran the built fix() on `<Text allowFontScaling={false} onPress={go}>Hi</Text>` with a snapshot node {interactive:true, allowFontScaling:false} (missing-role + font-scaling-disabled). Output file: `<Textn" allowFontScaling={false} onPress={go}>Hi</Text>` and renderFix reported 'Fixed 2 issues'. Line 177 sorts equal-start splices so the insertion precedes the range; line 185 applies them descending by start but the range's `end` is not shifted after the insertion.  
  Fix: Apply splices in an order that keeps earlier offsets valid: sort by `b.start - a.start || b.end - a.end` so at an equal start the removal range is applied before the zero-width insertion (then the insertion's offset is still correct); or rebuild the output in one forward pass from the original text. Add a test with a removal and an insertion on the same element.

- **Unauthenticated out-of-project file write on the Metro dev server / `v6y dev` via unsanitized snapshot.platform** (`packages/cli/src/index.ts:206`; security; from security; confidence 1)  
  Claim: handleReport sanitizes snapshot.screen with replace(/[^\w.-]+/g,'_') but interpolates snapshot.platform into the output filename unsanitized, so a POSTed snapshot with platform containing '../' writes its JSON file to an arbitrary path outside .v6y/snapshots and outside the project.  
  Evidence: Line 206: fs.writeFileSync(path.join(outDir, `${safe}.${snapshot.platform}.json`), ...). isSnapshot()/snapshotFrom() (index.ts:86-96) and readReport (index.ts:213-232) never validate platform. I called the built handleReport({snapshot:{screen:'Home',platform:'../../written-outside-snapshots-dir',root:{children:[]}}, issues:[], suppressed:[]}, {cwd: proj}) and the file was written to proj's PARENT directory (probeA/written-outside-snapshots-dir.json), outside both .v6y/snapshots and the project dir. This sink is reached with no authentication by the Metro middleware (packages/metro/src/index.ts:130-141 `receive`) and `v6y dev` (index.ts:235-262) on any POST to /v6y/report; neither checks Origin/Host, so any device on the LAN -- or a malicious web page the developer has open, via a no-preflight text/plain POST that the server JSON.parses regardless of content-type -- can trigger it while the dev server runs. Content written is JSON.stringify of the attacker's snapshot (attacker-controlled JSON), extension forced to .json.  
  Fix: Sanitize platform the same way as screen (or hard-restrict to an enum ios|android|unknown), and after building the path assert the resolved target stays within outDir (path.resolve(outDir, name) and check it startsWith(outDir + path.sep)). Apply the same platform sanitization in packages/react-native/src/jest.ts:117 (record()), which has the identical `${name}.${snapshot.platform}.json` pattern. Separately, bind the dev server to localhost by default and/or require a token, and validate the Host header (see the dev-server hardening finding).

  Claim: coverage() calls a snapshot stale for a changed file when the file's mtime is newer than capturedAt, and analyze() (index.ts:143-148) then drops every issue touching that file; a git checkout, `prettier --write`, lint --fix or branch switch bumps mtimes without changing the lines, so the gate passes vacuously.

- **`v6y fix` writes outside the project via path traversal in snapshot source.file** (`packages/cli/src/fix.ts:212`; security; from security; confidence 1)  
  Claim: fix resolves each edit target as path.join(cwd, issue.source.file) with no check that the result stays inside cwd, so a crafted snapshot whose node.source.file contains '../' makes `v6y fix` read and overwrite a file outside the project.  
  Evidence: fix.ts:212 `const abs = path.join(cwd, issue.source.file)`, :231 `fs.readFileSync(abs)`, :235 `fs.writeFileSync(abs, text)`. source.file flows unmodified from the snapshot JSON (engine.ts toIssue copies node.source). I verified path.join('/home/dev/app','../../../../../../tmp/other.tsx') === '/tmp/other.tsx'. ### security

Checked and found NOT exploitable (so I did not file them): (1) Prototype pollution via snapshot JSON keys -- snapshots go through JSON.parse (where "__proto__" becomes an own, non-prototype property) and are then read field-by-field; there is no deep-merge of attacker JSON into shared objects. The only object spread/merge is config option merging in resolveConfig (config.ts:152-168), which throws on any key not already in rule.defaultOptions, and config is trusted code anyway. (2) Shell injection in git calls -- changed.ts uses execFileSync('git', [..args]) with no shell, and the GitHub Action passes inputs via env and quotes them (`files=( $V6Y_SNAPSHOT_GLOB )` word-splits intentionally but cannot execute; `origin/$V6Y_BASE_REF` is quoted; github.base_ref is the base-repo branch, not fork-controlled). (3) githubAnnotations (changed.ts:114-126) embeds snapshot-controlled text (labels, colors, component/type names flow into rule messages) into the annotation body, but esc() encodes %, CR and LF (and escProp also : and ,), so a crafted label cannot inject a new ::workflow command -- the escaping is what prevents it; keep it.

By design but worth the user knowing: the MCP `projectDir` argument lets an agent point v6y at any directory (monorepo support) and then git runs and snapshots are read there -- this is intended, but it is the realistic delivery path for the `v6y fix` traversal finding when combined with a repo that ships malicious snapshots. The Claude Code PreToolUse hook runs the project-local node_modules/.bin/v6y (pre-commit-check.mjs:21-27); executing a repo-local bin is standard (post-`npm install` the repo's postinstall already ran), so this is acceptable, but note it runs automatically on Claude's commit attempts in any repo that has both .v6y/snapshots/ and that bin.

Could not fully verify: the realistic blast radius of the `v6y fix` traversal write to an EXTERNAL file (finding B) depends on that file parsing as TS+JSX with a JSX element at the exact line:col -- I confirmed the unbounded path.join and the capturedAt bypass but did not construct an end-to-end external-file edit. The .mcp.json shell concern (finding H) depends on Claude Code's ${...} expansion order, which I could not determine from the repo.

The three field-test reports (v6y-field) measured precision/attribution only; none of them exercised any security or input-boundary behavior, so all of the above is net-new relative to what was already recorded.
